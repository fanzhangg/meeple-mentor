# 游戏内容解耦与多语言重构计划

状态：计划已制定；仅现有测试基线已执行，M0–M6 尚未完成。

## 目标与边界

最终验收目标：添加一个使用既有展示组件的新游戏，只需添加遵循约定的 Markdown 并运行常规构建/部署，不修改共享前端、服务端、公共翻译、测试实现或游戏白名单，不要求手写 JSON。图片和独立内容验收 Markdown 可选。切换语言不改变规则版本、答题结果、章节身份或会话身份。

架构以 [网站架构设计](site-architecture.md) 为准：Markdown 是唯一人工编辑的游戏内容源；Guide 与问答读取同一个 GameDocument 发布产物，不再分别生成和维护两套规则模型。

本轮保留原生 ES modules、Node HTTP 服务、现有 URL、静态托管能力、共享样式、聊天 JSON/SSE 协议和已审核规则。无需更换前端框架、引入数据库或开发通用桌游规则执行引擎。真实新组件需求仍允许扩展共享代码。

角色、图例、规则和测试补充已分别保存在 `18182f6` 与 `6cdc2ac`。实施前仍须确认最新迁移基线并保留后续工作；不得通过重置工作区或使用旧 HEAD 覆盖它们。内容变动与结构迁移分开审查。

## 全阶段完成规则

1. 每个 milestone 单独形成可审查、可回退的变更；前一阶段通过后才进入下一阶段。
2. 所有已引入的自动测试和该阶段专项测试必须通过。任意必需测试失败、跳过、超时或缺少执行环境，都不能标记完成。
3. 不降低有效覆盖、不降低阈值、不自动接受新截图来掩盖失败。现有游戏专属测试迁为通用执行器加独立验收数据；验证覆盖等价后移除旧实现，不要求维持原测试文件名或测试数量。
4. 规则文字、数值、例外、题目答案与来源映射必须保持。确有意图改变的行为单列，如缺少 slug 返回 400、HUANG 切换语言保留答案。
5. 自动化测试、构建校验、浏览器行为与视觉验收分别报告；截图只能补充语义断言。
6. 每阶段报告基线版本或文件清单、改动、准确命令、通过/失败/跳过数、浏览器矩阵结果、已知限制和回退方式。未执行的项目标记“未执行”。
7. 同一阶段修改完成后运行最终完整门槛；若之后再次修改相关代码，重新执行受影响检查及最终门槛。

“确保通过”通过以上合并门槛落实，不能预先宣称未来测试已经通过，也不能保证不存在任何未知缺陷。

## 测试代码与游戏规则解耦（全阶段硬约束）

- 测试实现不写真实游戏名称、slug 列表、角色数量、费用/得分数值、正确答案、特定章节 ID 或规则文本正则；不按真实游戏分支，也不直接 import 某游戏的数据模块。
- 单元与组件测试使用虚构的最小内容包，验证结构、评分机制、排序、语言回退、内容转义、检索和流式协议。虚构输入和预期结果显式给定，不依赖真实规则书。
- 真实游戏的集成/E2E 测试从内容清单发现游戏、语言和组件能力，通过同一参数化执行器运行；测试代码不枚举四个游戏或假设每个游戏都有题目、角色或附录。
- 规则事实及内容特定的验收预期放在独立的 `content-review/<slug>/acceptance.md`，使用 Markdown 与声明式 front matter；迁移基线放在同目录的 `baseline.md`。这些是数据，不包含 JavaScript、可执行表达式、自定义回调或逐游戏插件，也不进入产品构建或模型上下文。新游戏无需另建验收文件即可运行通用结构/行为测试；已有独立规则审核用例迁移后继续保留。
- 验收数据可描述审核版本、来源引用、预期内容片段/条目清单、检索查询及预期章节 ID。执行器只支持固定的通用检查类型，不创建“检查某游戏规则”的专属检查器。
- 正确答案能被渲染、选择和评分，属于代码测试；答案是否符合规则书，由独立内容审核及其验收数据负责。不能从待测产物自动生成同一份预期结果，再声称证明了规则正确。
- 原先关于特定角色数量、费用、图例顺序等保护必须迁入验收数据，保留来源与审核记录；后续更新规则或新增游戏只改这些数据，不修改测试实现。
- 每个 milestone 都检查此边界；最终新增测试游戏时，共享应用代码和测试代码的哈希均保持不变。

## 目标结构和契约

```text
content/games/<slug>/
  rules.en.md             # front matter + 规则、说明、练习、术语与来源
  rules.zh-CN.md          # 对应稳定 ID；至少有一种语言
  assets/                # 可选，纯 Markdown 游戏也可发布
content-review/<slug>/    # 独立审核的验收数据，不发布到产品
  acceptance.md           # 可选的规则事实与检索预期
  baseline.md             # 迁移项目的独立审核基线
tests/
  fixtures/               # 虚构内容包及通用边界输入
  unit/                   # 与真实游戏无关的机制测试
  integration/            # 自动发现内容包的通用测试
  e2e/                    # 按语言和组件能力参数化的浏览器流程
src/content/              # 契约、校验、加载、构建和迁移适配器
src/server/               # 检索、上下文构造、模型调用、HTTP 路由
public/shared/            # 指南渲染、答题、语言状态、共享交互
public/locales/           # 站点界面翻译
public/data/              # 同一个 GameDocument 产物和自动目录，前后端共读
public/games/<slug>/      # 生成的静态页面壳，保留原地址
```

上述是目标职责划分，实施时可保留已有共享文件路径以减少无效移动。源码内容和生成文件必须有明确边界。

- 统一解析模型 GameDocument：schemaVersion、slug、locale、rulesetId、contentVersion、metadata、sections/blocks、questions、glossary、sources、assets。规则正文就在内容节点中，不再额外维护独立的 guide 摘要数据与 chatbot rulebooks 字段。
- front matter 提供元数据，目录和可用语言由构建自动发现；生成 JSON 只用于传输，不允许人工编辑。
- supportedLocales 可区分已审核发布与草稿；草稿不能静默成为线上回退来源。
- 游戏文本按语言维护 Markdown，结构和答案用稳定 ID；不再要求独立的游戏翻译 JSON 或逐句翻译键。
- 内容块至少覆盖段落、列表、表格、提醒、嵌套详情、多图片、图标列表、分步骤图例。图例顺序由数据声明，不按章节名特判。
- 语言规范化使用 en/zh-CN，并兼容旧 zh；requestedLocale、contentLocale、rulesetId 分开处理。缺少译本不得切换规则版本。
- 答题保存 questionId → optionId；展开状态保存 blockId；阅读位置保存 sectionId 与必要偏移，不按 DOM 数组索引保存。
- 内容文件路径限定在所属包内；slug、版本与资源引用必须校验。
- 公共规则优先级、失败策略属于代码；游戏规则、术语、例外和教学提纲属于 Markdown 内容。规则节点与练习题/错误选项区分类型，后端从同一模型构造可信规则上下文。
- Guide 与聊天请求使用同一内容版本；不匹配时提示刷新。全文搜索索引和 prompt 是可重建的派生视图，不是第二套人工维护的规则。

- 移走 HUANG 专用提纲、全局游戏术语、加载白名单；公共查询意图与游戏 glossary 分开。
- 中文规范化/分词策略由通用检索器负责，索引包含正文、提醒、图注、关键词与来源；未知问题明确无匹配。
- 从 GameDocument 的全部规则/说明节点构造上下文，含折叠细则、图注和角色补充资料；排除题目干扰选项、独立审核用例。不同时改成仅 top-k 检索，以免另引信息缺失回归。
- 聊天携带页面的 contentVersion，后端核对同游戏/语言/规则版本，版本不匹配时返回可识别状态并提示刷新。
- API 保持原 JSON/SSE 与旧 language: zh/en 兼容，可补充实际内容语言/版本。缺少 slug 明确返回 400，未知游戏 404；不支持的显式语言返回约定的错误。

专项测试：

- 按清单发现游戏和语言，验证 prompt 的内容来源与版本、已声明补充条目的完整性。用带唯一标记的两个虚构包验证隔离，不能以真实游戏共享词汇作为串用判据。
- 通用检索测试用虚构规则验证中文、同义词、短问句、排序和无匹配；真实查询及预期章节只存放在经过独立审核的 acceptance.md 中。
- 对比页面内容节点与后端规则上下文的完整性及哈希；验证折叠规则可用于回答、错误选项不作为规则、内容版本不匹配不会静默使用其他版本。
- 通用内容验收执行器自动加载全部检索验收数据；词表隔离由虚构包验证，不在测试代码中硬编码真实术语。
- 缺 slug、非法 slug、未知包、缺语言、坏历史、缺译本和无 key 模式按契约处理。
- 真实本地 HTTP + 模型替身测试 JSON/SSE：分片 UTF-8、首段增量、done、上游错误、超时、中断、断开取消、心跳、部分回答不入历史。
- 保留当前模型参数、Markdown 渲染与会话隔离回归。四游戏页面请求均兼容新服务端。

完成标准：服务端不认识具体游戏规则；无游戏白名单；所有协议、检索、语言和内容完整性测试通过。

回退：用相同兼容产物恢复旧 loader/路由实现，前端请求契约仍兼容。

## M6：移除兼容层，验证内容驱动扩展

依赖：M5。

交付：删除已无调用的旧加载器、重复指南/答题代码、HUANG 特判、双份手工目录和旧生成写入路径；更新 README、内容编写指南与迁移说明。保留来源审核、独立验收数据、通用测试执行器和离线导入工具。

专项测试：

- 在临时工作区只添加虚构游戏的 Markdown（含 front matter、规则和练习），不新增 JSON、图片或专属测试；构建后目录自动出现，静态页面、双语、题目和 API 均工作，通用测试自动覆盖新包，共享应用源码和测试源码哈希均保持不变。
- 测试包包含无题目、缺少可选语言、长标题、多图、图标和嵌套详情等边界；不混入生产游戏目录。
- 向通用 UI 添加测试语言，验证默认回退和按 ID 保存状态；无需新增页面分支。
- 删除测试包重建后无旧目录、资源或检索条目残留。
- 架构检查：服务端不能导入 public/games；共享运行代码和测试实现不含真实游戏 slug 特判或游戏名单，不直接导入具体游戏模块；生产运行不引用迁移适配器或验收数据。代码审查同时确认没有具体规则数值或文本断言，不能仅凭字符串扫描证明解耦。
- 从干净检出执行完整验证；对四个真实游戏运行最终内容审计、全部浏览器矩阵和两种托管模式验收。

完成标准：所有迁移兼容分支已移除；新增游戏只需 Markdown，图片及独立验收 Markdown 可选；Guide 与问答共读同一产物，测试实现不变；无失败、跳过或未执行的必需验收项。

回退：回退整个清理变更；生产回退使用同一历史版本的代码与构建产物，不能单独回退某一方。

## 测试矩阵与执行约定

| 层级 | 覆盖范围 | 引入阶段 | 每阶段要求 |
| --- | --- | --- | --- |
| 通用机制/API 测试 | 承接当前有效覆盖，使用虚构数据 | M0 | 全部执行，不能弱化 |
| 内容验收 | 自动发现的独立审核数据，由通用执行器运行 | M0 | 全量执行；规则事实不写入测试实现 |
| 内容契约 | 所有已发布包/语言 + 无效输入 | M1 | 全量校验 |

| 构建集成 | 幂等、清洁构建、版本一致、资源可达 | M2 | 全量执行 |
| i18n/状态 | 语言优先级、回退、稳定 ID、会话 | M3 | 全量执行 |
| 浏览器功能 | 清单发现的游戏 × 支持语言 × 2 托管方式 × 桌面/移动 | M0 起逐步充实 | 每阶段完成时全量执行 |
| 响应式与视觉 | 清单发现的游戏 × 支持语言 × 320/390/768/1280px | M0 建基线，M4 完整 | 共享 UI 改动时全量，其他阶段布局冒烟 |
| 检索/流式协议 | 虚构输入验证机制；真实查询来自独立验收数据 | M5 扩充 | 后端改动全量，现有回归始终执行 |

拟新增的命令（尚未实现）：

```text
npm run check
npm run validate:content
npm run test:content
npm run build
npm test
npm run test:build
npm run test:e2e
npm run verify
```

verify 是总入口，按依赖顺序运行当阶段已引入的全部检查，任一步失败即非零退出。M0 就包含迁移后的通用测试、独立内容验收与浏览器基线；新增阶段门槛必须加入总入口。test:content 用同一执行器加载 content-review 数据。单独命令用于定位失败，不替代最终完整验证。

自动化测试隔离开发者 .env.local，使用临时端口和临时输出目录，结束清理服务器，避免外网模型请求和污染真实内容。浏览器端记录控制台错误、网络失败、失败截图与 trace。CI 保存测试报告和失败产物，不在失败时继续发布。

视觉变化必须有人工解释与批准的基线更新；业务正确性以独立内容和行为断言为准。规则事实准确性仍由原始来源审核支持，测试不能替代规则审核。
