# 网站架构设计（待评审）

状态：设计稿，尚未实施。

## 核心约束

1. 游戏规则、教学说明、题目、答案、术语和游戏元数据只在 Markdown 中维护，不进入前后端或测试实现。
2. Guide 与问答读取同一份构建后的 GameDocument；不分别维护 guide 数据和 chatbot 规则。
3. 新增游戏只需增加遵循统一格式的 Markdown，常规构建/部署后自动出现在网站；不要求手写 JSON、页面、注册代码或测试代码。

## 数据流

```text
游戏 Markdown（唯一人工编辑来源）
              ↓
       统一解析、校验与构建
              ↓
     GameDocument（只读生成产物）
          ↙                  ↘
 Guide 渲染器             问答上下文构造器
 阅读、目录、练习          检索、引用、模型调用
```

JSON 可作为自动生成的传输格式，不是另一套编辑来源。浏览器和 Node 服务都读取同一发布产物，不各自重新解析、拼接或补充游戏规则。

## Markdown 内容约定

```text
content/games/<slug>/
  rules.zh-CN.md       # 中文文档
  rules.en.md          # 英文文档；支持语言从现有文档发现
  assets/             # 可选图片，无图片也能接入
content-review/<slug>/
  acceptance.md       # 可选的独立内容验收用例，不进入产品
```

- 每个游戏至少一份规则文档；每份文档用 YAML front matter 声明标题、语言、规则版本、默认语言等。无需单独 manifest.json。
- 正文使用 Markdown 标题、段落、列表、表格和图片；用统一的小范围声明语法标注稳定章节 ID、详情块、术语和练习题。题目包含稳定选项 ID、正确选项和解释；不允许执行脚本。
- 一个语言可以拆成多份 Markdown，由固定的文档声明方式指定身份与顺序；共享解析器检查引用、循环和重复 ID，不执行任意路径或代码。
- 规则、教学说明和例外均保留在同一文档模型中。页面的摘要/展开只是展示方式，折叠内容仍属于问答可用的完整规则。
- 练习题、错误选项和规则正文有不同的内容类型。问答从同一 GameDocument 选择规则及审核后的说明，不将干扰选项当作规则依据。
- front matter 只描述内容和展示顺序，不用配置表达式实现特定游戏逻辑。复杂样式由通用组件承担。

## 运行代码职责

| 模块 | 职责 |
| --- | --- |
| 内容构建器 | 自动发现 Markdown，校验引用与多语言身份，输出 GameDocument、目录和页面壳 |
| 共享 Guide | 根据内容类型渲染，管理目录、展开、练习与阅读状态 |
| 共享语言模块 | 公共界面翻译、内容语言选择、回退；不存放游戏规则 |
| 问答服务 | 加载相同 GameDocument，生成通用上下文，调用模型并流式返回 |
| 通用测试 | 使用虚构 Markdown 验证机制；自动发现真实文档进行结构和集成校验 |

指南支持静态托管；聊天独立依赖服务端。前端不需要先读取游戏 API 再回退另一份静态内容。模型密钥仅在后端。

## 多语言与发布一致性

- 章节、题目和选项通过稳定 ID 跨语言对应；切换语言不重置答案、阅读状态或聊天历史。
- 语言与规则版本独立。缺少翻译时明确展示实际内容语言，不静默换用另一规则版本。
- GameDocument 含 slug、locale、rulesetId 和内容版本哈希。聊天携带当前页面的内容版本，后端必须使用同版本；版本不匹配时提示刷新，不静默回答另一版规则。
- 静态站点和问答服务发布同一构建产物。检索索引是从 GameDocument 生成的可重建派生数据，不是独立规则来源。

## 验收

- 在临时目录只添加虚构游戏 Markdown，通用构建自动生成目录、页面、练习与问答数据；不新增图片也能通过完整流程。
- 同一条 Markdown 规则修改后，页面展示与问答上下文读取同一新节点和版本；包括折叠详情、图注及补充条目。
- 测试覆盖错误选项不进入规则上下文、跨游戏隔离、语言回退、内容版本不匹配和缺少题目的合法文档。
- 新增游戏前后，共享应用源码和测试源码哈希不变。真实规则预期如需保存，仅写独立验收 Markdown；游戏专属规则不写入测试代码。
- 旧内容迁移后无重复编辑来源。每个 milestone 的完整测试门槛继续执行。
